# Workspace Writing Plan

用于已批准书面设计后的实施计划草案、计划自审和执行确认。它共享 `feature.design` 锚点，不新增 Core Stage。

## 前置条件

读取当前需求、已批准的 `design/design.md`、已确认的按需设计附件、仓内约定和相关代码。主设计是每项计划的必读来源；附件只在任务需要其细节时追加读取。书面设计未获用户批准时停止并回到 `workspace-feature-design`；轻量改动不使用本 Skill。

## 生成计划

书面设计获批后直接读取 `templates/feature/implementation.md`，在 `plans/implementation.md` 写唯一书面计划草案并从 README 链接，不先展示摘要等待生成确认；写完实际内容后删除示例和无关章节，并将 README 的计划审阅记为“待审阅”。只有任务、基线、分支、执行方式或验证方式存在无法从设计、规范和代码事实解决的关键阻塞时才询问。需求仍保持 `planning`。先检查设计是否包含可独立交付的子系统；能独立验收的子系统拆成不同需求或计划。

尚未生成计划时，如解决关键阻塞需要定向修订已批准的设计或附件，提问前列出具体修订、受影响文件和可观察影响，并说明用户的明确选择将同时批准该修订并继续生成计划。用户明确选择后，只写回已披露内容并完成设计自审，保持设计审阅为“已批准”，不再请求同一修订的设计批准，随后继续生成计划；新生成的计划审阅仍为“待审阅”。已有计划，或写回时发现未披露或超出用户选择的实质变化，则将相应文档退回待审阅并停止。

计划必须不依赖历史对话即可在新 Agent 窗口执行，但不复制需求、设计或仓规范全文。新计划写入唯一 `task-evidence-v2` 完成门禁；旧 `task-evidence-v1` 计划只读兼容。按“目标与方案 → 执行概览 → 任务 → 整体验证与完成条件”组织。执行概览写明当前迭代、Workflow Run、启动读取清单、feature slug、目标仓、基线、分支、当前工作目录、执行方式和全局约束。日常只读取当前文档，历史迭代只在追溯时读取。

执行方式随计划一起审阅，不增加独立确认轮次：默认“单 Agent”连续实现、验证和自审；“按需子 Agent”只为独立任务或有明确收益的关键审查分派；“每任务子 Agent”由独立实现者完成，并检查需求符合性和代码质量。三种方式都不自动并行、创建 worktree、commit 或 push。

先整理任务骨架：任务标题、可观察交付结果、唯一目标仓、显式依赖和验证性质。跨仓交付拆为不同任务并通过契约连接，同仓按主要行为闭环拆分；能分别实现、验证和接受的业务流程不得混在一项，同一行为的数据组合和必要测试可以合并。不按技术层、文件数、固定分钟数或 Case 数机械拆分。只有存在至少两个自然业务或交付领域时才增加三级标题分组。

骨架完成后做一次语义和代码事实预检：逐个核对需求验收点是否由 D 决策、任务和验证承接，再核对已有模块、文件和符号或明确的 Create 目标，提供与消费接口、任务边界和依赖、验证命令、环境与授权前提。编号映射用于发现遗漏，不能代替内容判断；`brief --check` 只负责确定性的结构诊断。

每个任务是独立、可验证的交付单元，使用顶层 `- [ ] T01 任务标题`，内部不使用嵌套任务复选框。只有审查者可能独立接受或拒绝时才拆分；多个能分别实现、验证和接受的业务流程不得塞入同一任务。标题下先用一至两句话说明交付结果，再写稳定的 `依据：` 和 `依赖：` 字段。依赖只允许“无”或显式编号列表，不使用 `T01-T03` 等范围缩写。测试、实现、配置和必要文档归入服务同一结果的任务，不按技术层横向分批。简单任务省略没有内容的区块；其他任务按交付结果、依据与依赖、文件、接口、实施步骤和验证组织。每项至少写明：

- 主设计的 R/D 编号或链接，并定位本任务承接的验收点；需要实现细节时，再附加设计附件的稳定章节链接；
- 唯一目标仓，以及以 Create、Modify、Test、Delete 或 Verify 标识的完整仓内相对文件路径；修改现有逻辑时写明稳定符号；
- 提供或消费的接口与前置依赖，或“无”；
- `行为`、`声明式` 或 `持久化` 的唯一验证性质；
- 独立验证区块中的工作目录、精确命令及通过条件；
- 非平凡行为的最小失败场景、实现结果和必要回归，或声明式变化的最小有效检查。

依赖只表达真实前置条件，不把阅读顺序或期望执行顺序伪装成依赖。实施步骤每步只表达一个动作及其可观察结果；非平凡行为写明具体失败场景、目标检查和预期失败原因。持久化任务必须包含结构、迁移或集成级真实写入检查，编译或纯 Mock 不能作为唯一验证。完全相同的整体验证只维护一次。不要求逐任务 commit、独立 worktree、内嵌完整实现代码或机械化分钟级步骤。

需要另行授权的数据库、真实 Provider、部署、生产迁移或跨团队联调列入“待外部验证”，不无条件阻塞无关本地任务；只有后续任务必须消费其真实结果时才建立依赖。

普通代码漂移，以及不改变目标、验收、公共契约、关键方案、验证强度、目标仓或副作用的任务内部细化，修正计划事实并继续。改变任务边界、验证强度、公共契约、关键方案、目标仓或副作用时，修订受影响文档并按变更规模审阅。

## 计划自审与确认

写入后完成三类自审：内容检查需求覆盖、任务边界、接口一致、关键假设、验证有效性和上述代码事实预检；结构检查运行 `python3 scripts/kit.py brief <slug> --check --json`，核对任务数、编号、依赖和引用；阅读检查查看 Markdown 预览中的标题导航、重点顺序、块间空行、列表缩进和长命令。预览不可用时检查源文件块结构并说明限制。确认没有 TBD、占位描述或泛化的“补测试”步骤。工具或预览检查不能替代语义判断和用户审阅。

向用户展示实际计划文件、工作类型、基线、候选分支及执行方式，等待批准。当前只有这一个审阅对象时，按根规则接受无附加条件的简短肯定回复。批准后立即去除草案标记、将 README 的计划审阅记为“已批准”、更新 README 为 `development`，并在用户没有要求“只审阅”或“暂不执行”时于同一轮转交 `workspace-execute-plan`。计划只有这一轮针对实际文件和执行条件的批准门禁；已批准条件在后续 Skill 中持续有效。

## 边界

本 Skill 不创建或切换分支，不实现代码，不 commit、push、合并、提测或运行外部环境。分支候选由 `python3 scripts/workspace_registry.py branch <repo> --type <type> --slug <slug> --json` 计算，直接使用返回的 `baseBranch` 和 `branch`，不得手工替换命名模板。
