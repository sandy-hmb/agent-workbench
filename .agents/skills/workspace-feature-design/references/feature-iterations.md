# 同一 Feature 的后续迭代

同一业务能力的需求变更继续使用原 feature slug 和固定文档入口。当前 Requirements 与 Design 维护完整的最新目标规格；当前 Plan 与 Verification 只描述本轮交付。不要因一次变更在工作台中创建另一个业务 Feature。

## 何时原地修订

- 仍在澄清或设计：直接修改受影响内容。
- 正在实现：修改未完成任务，必要时追加任务；已经完成的任务及当时证据不得改写成新结果。
- 实现不符合原验收：沿用原 R/D 修复；只有修复需要完整计划时才开启同一 Feature 的修复迭代。
- 已实现但尚未完成验收：默认继续当前迭代，不把它归档成已交付。

## 何时开启下一迭代

上一轮已经结束，且新增行为或实质改变现有规则时，开启下一迭代。首次开发或重大变更逐阶段审阅；范围明确、沿用关键方案且不改变高风险数据、权限语义或外部影响的小迭代，可以一次准备 Requirements 差异、必要 Design 调整和 Plan，并让用户审阅整个实际文档包。

开启下一轮时：

1. 使用 `i01`、`i02` 递增编号；已有未编号 Feature 首次轮转视为 `i01`，不按任务编号猜测轮次。
2. 先把当前 README、Requirements、Design 及附件、Plan、Verification 和必要的小型 Feature 产物复制到临时归档目录，核对完整后在同一文件系统重命名为 `history/<iteration>/`。不得递归复制既有 `history/`、业务仓、凭据或大型测试报告；失败时保留当前入口不变。
3. 在 `history/index.md` 记录轮次、当时状态、日期和入口，并从当前 README 链接该索引。归档保持原目录结构；若原 README 的历史链接在归档位置失效，由索引承担导航，不修改其他历史正文。
4. 顶层 Requirements 与 Design 更新为当前完整规格；顶层 Plan 替换为本轮增量任务，Verification 在产生新证据时重新创建。旧证据不得解锁新任务。
5. 新轮任务可从 T01 开始，其身份是“Feature＋迭代＋任务编号”。README 必须记录当前迭代，避免只凭任务编号引用证据。
6. 将生命周期重新置为 `planning`。启用 Workflow 时以 `<slug>-<iteration>` 作为现有 `--run-id`；同轮复用，新轮不得复用旧轮 Action 状态。

日常接手只读取顶层当前文档。历史内容只有追溯旧决策或证据时才从 `history/index.md` 按链接读取；历史不能参与当前任务解析、默认搜索或 handoff。

R/D 编号在同一 Feature 内保持稳定。新增定义使用未占用编号；改变原行为时修改其定义并在本轮变更中说明；移除行为保留简短停用说明，完整旧定义由历史归档承接。
